# Version 2.0.0 standalone application plan

[Version plans](README.md) · [Backlog](../BACKLOG.md) · [Maintenance](../MAINTENANCE.md) · [中文详细计划](../../plan/2.0.0.md)

The Chinese plan is the sole detailed implementation roadmap for the standalone application. It defines the source audit, target architecture, numbered work packages, dependencies, evidence, risks and exit criteria. Backlog alone tracks task status and priority; this page is a scope summary, not a second progress list. No release date is promised.

The goal is a maintainable application built from complete source, without runtime or build dependence on the modified legacy bundle, its internal module numbers, monkey patches or AST integration scripts. Preserve local tasks, timer, calendar, history, reports, forest, achievements, settings, backup, Chinese and English behavior and data. Cloud accounts and sync, groups and online rankings remain out of scope; historical compatibility records must be retained. Resource-table migration, a new backup container and large-backup optimization require separate justification and acceptance.

React, TypeScript and Vite are the preferred candidate, subject to an isolation, licensing, offline, browser, project-subpath and portable-package prototype. Reuse validated business logic through explicit service interfaces; rebuild UI boundaries that depend on the old React, Redux or DOM. The sequence is: A audit and baseline; B isolated skeleton; C core services; D independent UI; E switch and retire legacy dependencies only after acceptance; F full verification and release preparation. C and D can overlap only where their service contracts are ready.

The Phase B implementation and reproducible prototype evidence are described in the [engineering report](2.0.0-skeleton.md), with exact dependency decisions in the [dependency record](2.0.0-dependencies.md). Under the user's current constraint, `refactor/standalone-app` must not be merged into `main`, `dev` or any other branch. Passing a phase does not authorize a merge or release.

The [first D workspace report](2.0.0-ui-batch-1.md) records batch evidence; remaining scope and acceptance status stay in BACKLOG E09. Partial delivery does not replace the detailed D exit criteria.

The user's 2026-11-08 gate changes the sequence to **D functional migration → mandatory D-R human review → explicit user authorization → D-V concentrated visual restoration**, then consideration of E/F. Faithfully restore all local 1.9.x pages, components, entries and interactions without redesign, simplification or legacy-bundle runtime dependencies. D prioritizes complete working functionality; temporary visual differences are allowed, inoperative placeholders are not. Before D exit, independently build/start the candidate and functionally test every page so no rendering/runtime error blocks manual inspection.

At D-R, deliver an actually runnable isolated preview, startup/stop instructions, baseline references, per-page entry points and known functional/interaction/visual differences. Pause subsequent development and await the user's inspection and explicit feedback. Record and organize their findings in BACKLOG E09; automated passes or silence do not authorize D-V. Only the user's completed D-R and explicit consent permit concentrated visual work. Do not automatically enter D-V, E or F, or declare visual restoration complete on the user's behalf. E/F remain subject to their own conditions and authorization.

The existing application database `PomodoroDB6` v3, backup format versions, legacy `Version='6.5'` and the product version are distinct. Never reset data for a version rename. Test real, authorized long-lived copies and historical backups in isolation, transaction failures, recovery and concurrent old/new clients. Old clients may not respect a new locking protocol; prohibit unsafe combinations and document downgrade limits. Version 2.0.0 uses an independent three-part application version and tag, with 7.1.1 retained as provenance; update generation, display, history, read state, caching, packaging and release gates without rewriting historical tags or releases.

Compare functionality, visual behavior and performance with recorded reproducible baselines. Verify offline operation, network controls, supported browsers, notifications, Pages project subpaths, extracted ZIP/tar.gz startup, CI and license/notice obligations. The user confirms redistribution permission has been obtained. Real Safari, system notifications and long-lived data require actual evidence. `main` remains the stable branch and sole official Pages source; implementation stays on the dedicated branch until final acceptance. See the [detailed plan](../../plan/2.0.0.md) and [Backlog](../BACKLOG.md) for current status.
