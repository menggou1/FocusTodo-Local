## 3. 备份格式与界面方案

### 3.1 先完成完整压缩备份

1. 保留现有快照和事务边界，先生成紧凑 JSON，再压缩；优先评估 Gzip，使用可识别的 `.json.gz` 扩展名。
2. 导入同时支持原有 v1/v2 JSON 和新压缩文件；按文件内容识别格式，扩展名只作为提示。格式识别和解压失败时明确报错。
3. 压缩只改变外层编码时，不因压缩本身升级数据库或业务数据结构；新增资源清单等结构变化才引入新的备份格式版本。
4. 明确兼容方向：新版读取旧备份；旧版不会自动支持新压缩格式。保留普通 JSON 导出入口供排查和兼容使用。
5. 检测浏览器压缩能力；不支持时提供普通 JSON 回退，并在界面说明实际导出格式。是否引入压缩依赖由目标浏览器覆盖决定。

### 3.2 提供体积分析和壁纸选项

- 显示任务、专注记录、其他数据、图片资源的体积与记录数；生成前可显示估算值，生成后显示实际文件大小。
- 默认导出完整数据，用户可以选择不包含壁纸；名称、文件内范围标记和导入确认均说明是否包含图片。
- 不含壁纸时仍保留任务和专注明细。导入后使用可用的默认主题，清理或映射无法解析的激活主题引用，不留下指向缺失图片的状态。
- 导入前自动备份与删除前备份仍采用完整范围，不沿用用户上一次“不含壁纸”的选项。
- 浏览器下载发起与磁盘保存完成分开表述，不能在无法确认落盘时提示“已安全保存”。

### 3.3 图片独立资源格式（后续阶段）

在完整 Gzip 方案稳定后，评估 ZIP 内放置数据 JSON、资源清单和二进制图片。ZIP 与 Gzip 是两个阶段的候选格式，不要求首版同时实现两套压缩导出。

- 用内容摘要识别并去重图片，主题通过资源 ID 引用；二进制图片避免 Base64 约三分之一的编码开销。
- 缩略图从原图重建，验证恢复后的主题预览和激活状态；不将缩略图重建误写为原图重新压缩。
- 保留原图字节；有损降低图片质量只能作为用户明确选择的独立功能，不属于默认无损备份。
- 资源清单标明格式版本、备份范围、表记录数、资源引用及校验信息。校验用于发现损坏，不等同于证明文件来源可信。
- 先验证资源完整性再进入覆盖事务，拒绝损坏、缺图、未知版本或超出合理解压大小的文件。

## 4. 历史待办：本版优先处理

### 4.1 无 Web Locks 的维护互斥（P0）

来源：[patch.1 后续方案](UPDATE-7.1.1-patch.1.md)、[1.1.0 未完成事项](UPDATE-7.1.1-local.1.1.0.md)、[当前维护边界](MAINTENANCE.md#6-待修复与验收边界)。计时事务去重已有覆盖，不能据此认定并发导入/删除安全。

计划让 LocalMeta 维护标记携带操作拥有者、操作 ID 和恢复阶段，在 IndexedDB 事务内校验归属。新页启动和故障恢复必须区分活跃维护与遗留状态；不能只按超时直接清除标记，也不能由非拥有者覆盖有效日志。

验收覆盖两页同时导入、导入与删除竞争、维护期间第三页启动、维护页关闭或进程结束、设置恢复失败、刷新后重试。要求无混合数据、无他页误清维护标记、失败可恢复，旧计时写入不能穿透维护边界。

### 4.2 主题迁移和多设置一致性（P1）

来源同上。现有主题原图和缩略图放在 localStorage，主题内容、激活 ID 与 Theme 分键更新。

计划将图片迁入 IndexedDB 的 Blob/资源表，保存可恢复的迁移状态；先复制、校验、切换引用，确认成功后再清理旧数据。不能将 IndexedDB 与 localStorage 假定为一个原子事务，需要日志和恢复规则；主题元信息尽量放在同一数据库事务，兼容镜像写入可重试。

验收覆盖旧 data URL 迁移、原有主题与 Bing 主题、旧 JSON 导入、配额不足、迁移中断、重复启动、资源写入或设置写入失败。迁移失败保留旧图片与可用配置，不显示成功状态。若需要升级数据库，单独列出升级步骤与回退限制；不能靠删库或直接覆盖旧版代码回退。

### 4.3 大数据与恢复性能（P1）

用独立生成的数据准备约 1 MB、10 MB、50 MB 的未压缩样本，分别覆盖大量任务/历史和图片占比较高两类。记录导出、压缩、解压、校验、恢复耗时，界面响应及可测的内存峰值；报告测试浏览器、设备与数据规模，不预先承诺固定耗时。

根据测量决定是否分批读取、后台计算或使用流式压缩，减少现有 getAll、完整序列化和多次复制的峰值。读写方案必须维持一致快照与事务恢复语义。另测长区间恢复的大量记录广播；如记录数组确有瓶颈，再评估广播提交批次 ID 并查询数据库。

## 7. 实施顺序与验收门槛

1. **格式和兼容设计**：确定 Gzip 外层、导出范围标记和旧 JSON 兼容；制定迁移与维护拥有者方案，不先改数据库版本。
2. **最小完整闭环**：紧凑 JSON → 压缩下载 → 文件选择 → 解压校验 → 导入前完整备份 → 原子替换/故障恢复。
3. **并发维护保护**：完成无 Web Locks 的竞争、中断和恢复用例，确保其他页面不能破坏维护。
4. **主题与资源阶段**：完成体积分析和壁纸选择；Blob 迁移、资源包在各自回滚和兼容验收通过后接入。若后移，明确本版仍保留 data URL，并不宣称主题迁移完成。
5. **容量与真实环境**：先测大数据与人工完整恢复，再按第 5 节逐项扩大覆盖，记录实际结果和结转项。

本版核心验收条件：

- [ ] 旧 v1/v2 JSON、普通 JSON 和新压缩备份按支持范围正确导入；未知版本、损坏或超限解压不会覆盖当前数据。
- [ ] 完整往返恢复后，任务/子任务/项目 ID 与关联、专注时段和时长、设置、图片及计时快照语义一致；恢复确认状态允许按既有导入规则转换，不能自动运行并计入离线时间。
- [ ] 记录数、ID 和字段核对之外，验证统计总时长、任务进度和实际主题显示；无丢失、重复或混合状态。
- [ ] 不含壁纸备份的范围标记和导入提示一致，任务/历史完整，主题回退正常；自动安全备份始终完整。
- [ ] 解压、校验、数据库写入、设置写入或迁移失败时可恢复；未完成事务不提示成功。
- [ ] 无 Web Locks 并发维护专项通过，保留现有计时事务去重和跨标签页初始化回归。
- [ ] 使用脱敏或生成数据复现实测压缩收益；不把私人备份、凭证、任务文字或图片加入仓库和 CI 产物。
- [ ] 记录容量测量和人工落盘再导回结果，未覆盖环境写入最终报告。

实际开发后按维护指南运行发布生成、核心/服务/启动/发布检查、语法与完整浏览器验收；涉及发布包时执行 ZIP/tar.gz 解压启动和包内链接检查。正式发布仍使用三系统 Node.js 22/24 门禁；测试使用独立端口和浏览器上下文，不在日常用户数据库上做覆盖试验。
